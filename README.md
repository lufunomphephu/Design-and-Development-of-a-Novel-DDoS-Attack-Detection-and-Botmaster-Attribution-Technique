# DDoS Detection & Botmaster Attribution — Prototype

Working prototype for the multi-signal DDoS detection and unsupervised
botmaster/C2 attribution pipeline described in the accompanying report.
This README covers everything needed to reproduce every quantitative
result in the report from scratch.

## 1. Requirements

- Python 3.10+ (developed and tested on 3.12)
- Packages: `pandas`, `numpy`, `scipy`, `matplotlib`, `scikit-learn`

Install with:

```bash
pip install pandas numpy scipy matplotlib scikit-learn
```

No GPU, no training step, and no random seeds are involved anywhere in
the pipeline — every result below is deterministic given the same input
data.

## 2. Getting the data

The prototype runs against the CTU-13 botnet dataset (García et al.,
2014), specifically **Scenario 10** and **Scenario 11**, both `rbot`
IRC-based botnets with DDoS (UDP/ICMP flood) activity.

1. Download the two scenarios' `.binetflow` files from the Stratosphere
   IPS project: <https://www.stratosphereips.org/datasets-ctu13>
   - Scenario 10 file used here: `capture20110818.binetflow`
   - Scenario 11 file used here: `capture20110818-2.binetflow`
2. Place the file(s) in the same directory as the notebook (the code
   expects `capture20110818.binetflow` by filename, in the working
   directory — see Section 1 of the notebook if you need to point it at
   a different path).

CTU-13 is a public research dataset and is used here strictly for
evaluation; no traffic was generated, scanned, or attacked as part of
this project.

## 3. Running the prototype

1. Open `Scenario10_Attribution_Pipeline_Updated.ipynb` in Jupyter
   (`jupyter notebook` or `jupyter lab`, or VS Code's notebook support).
2. **Restart the kernel and run all cells top to bottom** (Kernel →
   Restart & Run All). The cells depend on each other in sequence —
   running out of order or restarting partway through will raise
   `NameError`s for variables defined in earlier cells.
3. Expected runtime: **~30 seconds** on a single CPU core for the full
   Scenario 10 run (1.3M flow records); see Section 7.2 of the report
   for the per-stage breakdown.

### What each stage produces

| Stage | Notebook section | Output |
|---|---|---|
| Detection | §1–3 | Precision/recall/F1 (episode-level); per-window confusion matrix; ROC curve + AUC (`detection_roc_curve.png`) |
| Candidate discovery | §4.2 | Set of candidate hosts (pre-attack contact with the bot set) |
| Attribution (timing/rhythm/structure/fusion) | §5 | Per-host signal scores, composite ranking, Top-k accuracy, MRR |
| Ablation | §11 | Margin/MRR for every single-signal and paired-signal subset |

To run against Scenario 11 instead: change the CSV filename and the
`known_attacks` / bot-IP ground-truth lists in the early cells to match
Scenario 11's README (values already used for Scenario 11's reported
numbers are in the report's Section 5.3 table, for cross-checking).

## 4. Known limitations of this prototype (see report Section 6.2 for full discussion)

- Candidate discovery currently assumes the bot-set IPs are already
  known (from CTU-13's ground truth) to seed the "pre-attack contact"
  filter — a production deployment would need a separate step to
  generate this candidate set without ground truth.
- Tested only against UDP/ICMP volumetric floods; not evaluated against
  protocol- or application-layer attacks.
- No independent (literature) baseline is implemented; the ablation
  study's single-signal variants serve as an internal comparison only.

## 5. Reproducing this specific report's numbers

All numbers in the report were generated by running this exact notebook
against the two CTU-13 files above, with no manual editing of any
computed value. The confusion-matrix/ROC cells (§4.1) require
`scikit-learn`; every other cell only needs the packages listed in
Section 1.
